# Wardley maps

Maps are written as Mermaid (`wardley-beta`) in the deck's workspace, `workspaces/<deck>/diagrams/<name>.mmd`,
rendered to `workspaces/<deck>/assets/diagrams/<name>.svg` by `node scripts/render-diagrams.mjs -w <deck>`, and
placed on a slide as an image (`assets/diagrams/<name>.svg`, relative to the deck). The DDD Belgium maps are in
`workspaces/ddd-belgium-wardley/`; their reveal steps are generated by `scripts/gen-reveal.mjs`, which writes
into that workspace. The root `diagrams/` holds only the example maps (`npm run diagrams` renders those). For
the slide around the map, follow the `galaxitech-slides` skill (eyebrow, one-line title, then the image).

## Workflow

1. Write `workspaces/<deck>/diagrams/<name>.mmd` (start from the root `diagrams/wardley-workshop.mmd`).
2. Run `node scripts/render-diagrams.mjs -w <deck> <name>` from the repo root. Fix every `error:` and act on
   every `warn:` (move a component, or use a customisation comment below). Exit code 1 means errors.
3. Put it on a slide and run the deck validator, as the slides skill says:
   ```markdown
   ### Strategy · Wardley map

   # Where workshop effort should go

   ![Wardley map of …, short description for screen readers](assets/diagrams/<name>.svg)
   ```
4. Look at the slide screenshot. The checks measure overlap; only your eyes judge whether the map tells the story.

## Reading the map (so the coordinates mean something)

- **y = visibility** to the user, 1 at the top. The user sits at the top, their needs just below, and the things
  those depend on further down the value chain.
- **x = evolution**: Genesis (0–0.25), Custom built (0.25–0.5), Product (0.5–0.75), Commodity (0.75–1).
- Coordinates are `[visibility, evolution]`, both 0–1, as in OnlineWardleyMaps. Visibility comes first, which is
  the opposite of x, y; getting it backwards is the most common mistake.

## Source format

```mermaid
wardley-beta
size [1088, 456]

anchor "Product team" [0.94, 0.62]
component "Shared language" [0.80, 0.34]
component "Event Storming" [0.52, 0.46]
component "Facilitation" [0.38, 0.22] (inertia)
component "Online whiteboard" [0.24, 0.74] (buy)

"Product team" -> "Shared language"
"Shared language" -> "Event Storming"
"Event Storming" -> "Facilitation"
"Event Storming" -> "Online whiteboard"

evolve "Facilitation" 0.52
```

- `size [1088, 456]` for a map under a slide title (the body area, shown at 1:1), or `size [1280, 720]` for a full-slide map on a `map` slide (see below).
- Quote every name. Keep names to 1–3 words, at most about 20 characters.
- Strategy marks Mermaid supports: `(build)`, `(buy)`, `(outsource)`, `(market)`, `(inertia)`. Also `evolve`,
  `pipeline`, `note`, `annotation`, `accelerator`, `deaccelerator`. See the Mermaid Wardley docs for these.
- 6–10 components per slide. More than 12 won't read from the back of a room; split the map or zoom into part of
  the chain.

## House conventions (the renderer applies these; don't fake them)

| What | How it's drawn | How it's decided |
| --- | --- | --- |
| **User** | person icon in a ring, semibold label | every `anchor` |
| **User need** | gold ring with a gold centre dot, semibold label | every component a user links to directly (`"User" -> "Need"`) |
| Other components | white ring | |
| **Label side** | left of the node on the left half of the map, right of it on the right half, vertically centred, clear of the node's own marks | automatic |
| Label with an evolve arrow on the right half | above the node, so it doesn't sit on the arrow | automatic |
| Evolve arrows | gold, dashed, ending in a dashed gold **ghost ring** at the future position | automatic for every `evolve` |
| Labels | thin halo in the background colour, so a line passing behind stays legible | automatic |
| **Notes** | 16px ink, the same size as component labels, so they read from the back of a room. Notes count in the overlap checks like labels | automatic for every `note` (Mermaid's own 11px grey is never used) |
| Submap | a square around the node: this component has its own map | `%% submap "Name"` |
| Constraint | horizontal striped bar behind the node (the Theory of Constraints bottleneck) | `%% constraint "Name"` |
| Pipeline | stage labels centred below the box; the pipeline's own label above the box's left end | automatic for every `pipeline`. Keep notes and force arrows off the box's row; one row per arrow |

**Where a mark goes.** The state of a component *now* sits on the component: user need ring, constraint
bar, submap square. Forces on its *movement* sit on the evolution line: the evolve arrow, the inertia bar
(placed on the arrow, in the way of the move) and push / hold block arrows (`%% arrow-span E1 E2` draws them
slim and as long as the evolve arrows). A component with inertia but no evolve arrow keeps the bar just to
the right of the node, in the direction it would move.

Model needs as real links from the user; the gold mark follows from the structure. Use at most one user per map
unless the point of the slide is comparing users.

## Customisation

Customisation lives in Mermaid comments (`%%`), so the file is still valid Mermaid in any other tool.

| Comment | Effect |
| --- | --- |
| `%% label-side "Name" left\|right\|above\|below` | force where one label goes |
| `%% need "Name"` | mark a user need that the links don't show |
| `%% not-need "Name"` | a component the user links to that isn't presented as a need |
| `%% allow-crossing "Name"` | accept lines crossing this label (hubs with links in every direction). Say why in a comment above it |
| `%% constraint "Name"` | striped bar behind the component: the bottleneck |
| `%% submap "Name"` | square around the node: the component has its own map |
| `%% move "Name" E` | intended move (our own push): solid double-line arrow to a red ring at evolution E |
| `%% future "Name" ["Label"]` | the component's `evolve` line is the future state: drawn red, ghost ring red, optional red label |
| `%% past "Name" E ["Label"]` | where it came from: dashed ring at evolution E, dashed line into the node, muted label above (the name, or Label) |
| `%% future-link "A" "B"` | red line between the future positions of A and B (a move or future target, else the node) |
| `%% zone "Label" "#colour" v,e v,e v,e …` | a soft area behind the map (Peña's four action zones, the problem and solution domain, the layers of a value chain): a polygon of 3 to 10 corners in map coordinates, drawn with rounded corners as one connected shape, translucent, with its label at the top left inside. Keep shapes simple: a band, an L, a blob; no figure-eight. The label joins the overlap checks, the area does not |
| `%% dot V E` | an unnamed component ring, for a crowd of things inside a zone when the source names none (Peña p. 153). Dots block comments but carry no label |
| `%% pipeline-arrow "A" "B"` | inside a pipeline, people move from option A to option B (Wardley's server to cloud): red dashed arrow between the two nodes, B's ring red. No arrow means the options live side by side |
| `%% picture "assets/file.webp" V E W H` | a small image with its top-left corner at [V, E], W x H px, inlined into the SVG. Place it in empty space: it is not part of the overlap checks |
| `%% highlight "Text"` | a gold ring around the map text with exactly that content (a stage label, a note), and that text in bright semibold. Use one per reveal step to walk the audience through labels |
| `%% comment "Line one \| line two" "Component"` | **the way to comment on a component** (CJ, 13 Oct): a boxed, multi-line comment at 14px that the renderer places in a free area, with a thin diagonal line to the component's node (never horizontal or vertical: too easy to miss). Split lines with `\|`. The box joins the overlap checks. The search runs three passes, each looser; a warning says when the line had to cross a muted past/future label, and when no free area exists at all (shorten the text, or move a component). Prefer it over `note` and `note-for` for anything that comments on one component; keep `note` for narrative lines along the bottom of a reveal |
| `%% note-for "Note text" "Component"` | older form: a plain `note` with a thin line to the component's node. Superseded by `%% comment` |
| `%% label-size N` | component names (default 16px since 13 Oct; CJ found 17 a bit big). Use smaller sizes sparingly: 15 is the smallest that still reads from the back |

**Movement notation** (CJ's InfoQ Fig. 5, the EM map): a dashed line is natural evolution, past or
future; a solid double-line arrow is an intended move; red marks the future state. Red is used for
nothing else on a map.
| `note "Text" [v, e]` | a short note on the map (Mermaid syntax), drawn at label size. Keep it to one line of about 40 characters, and place it in empty space: it is checked for overlaps |
| `component "Name" [v, e] label [dx, dy]` | Mermaid's own offset; the renderer leaves that label exactly where Mermaid puts it |
| `%%{init: {"themeVariables": {"wardley": {"componentStroke": "#d6c9ab"}}}}%%` as the first line | per-map colours (keys: `backgroundColor`, `axisColor`, `axisTextColor`, `componentFill`, `componentStroke`, `componentLabelColor`, `linkStroke`, `evolutionStroke`, `annotationStroke`, `annotationTextColor`, `annotationFill`). Use design-system colours only. Font sizes are fixed for projection and can't be changed per map; Mermaid frontmatter `config:` is ignored too |

Prefer moving a component a little over adding comments. The coordinates are a judgement anyway, and a cleaner
map beats a clever override.

## Review: what the links mean

The layout checks below say nothing about whether the map is right. Before a map is called done,
answer three questions for every component, and write the answers that aren't obvious as `%%`
comments in the `.mmd`, so the next reader sees the reasoning:

1. **Who needs this?** There must be a link from above. If nobody needs it, it doesn't belong on the map.
2. **What does this need to work?** Links below. A component with nothing below it is a leaf: say
   why the map stops there (`%% leaf "Name"`), or add the link.
3. **If this stopped, which components above would break?** Every "breaks" is a link. This is the
   question that finds missing links: on the knowledge map the body of knowledge went stale without
   stewardship and unfindable without classification, so both links belong (CJ, 12 Oct).

Then check the shape of the chain: a link runs downward (the dependent sits higher), and a shortcut
link, A → C when A → B → C already exists, must be a real direct need (`%% direct-need "A" "C"`),
not a leftover. A hub with many direct needs is fine; a shortcut nobody can explain is not.

The renderer checks what it can (below). Each correction CJ makes to a map becomes a line here,
with the example that taught it.

## Checks (run on every render)

| Severity | Check | Typical fix |
| --- | --- | --- |
| error | a link runs upward | move the dependent above what it depends on, or turn the link around |
| warning | a component no user reaches | link it from a need, or remove it |
| warning | a shortcut link (A → C when A → B → C exists) | remove it, or `%% direct-need "A" "C"` with a comment saying why |
| warning | a component with nothing below it, outside commodity | add what it depends on, or `%% leaf "Name"` with a comment saying why the map stops there. Pipeline parents are exempt |
| — | `%% partial` (added by gen-reveal to every reveal step but the last) runs only the upward-link check; `%% no-graph-check` (legends) runs none | |
| error | a label runs off the map | move the component inwards, or `label-side` towards the middle |
| error | two labels overlap | move one component, or send one label to the other side |
| error | a label covers another component's node | same |
| warning | a link, evolve arrow or axis crosses a label | `label-side`, move the component, or `allow-crossing` for a hub |

`node scripts/render-diagrams.mjs --check tests/wardley-broken.mmd` runs the checks on a map without writing
anything. That file is a self-test with one case per check, and must exit with code 1.

## draw.io instead

Use draw.io only when the layout has to be hand-tuned beyond what coordinates express (dense annotations, a
workshop photo traced over). Keep it as `assets/diagrams/<name>.drawio.svg`, edit it in VS Code's draw.io
extension, and follow the same conventions by hand: person icon for users, gold ring and dot for needs, labels on
the outer side, gold evolve arrows, design-system colours, Sora. `assets/diagrams/wardley-workshop.drawio.svg`
shows them. The overlap checks don't run on draw.io files, so check the slide screenshot carefully.

## Full-slide maps

When the map is the slide, use the `map` slide class: the map fills all 1280 × 720 and the only chrome is a small
label chip, a small star and the page number. Render it at `size [1280, 720]` (keep a separate `<name>-full.mmd`
if the same map also appears under a title). `diagrams/wardley-workshop-full.mmd` is the example.

```markdown
<!-- _class: map -->

### Wardley map · full slide

![Wardley map of …](assets/diagrams/wardley-workshop-full.svg)
```

The label chip covers the top-left corner (about 280 × 32), so keep components out of that corner: visibility
above ~0.92 with evolution below ~0.2.
